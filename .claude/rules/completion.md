# 仕事が終わったときのルール

社長が Claude Code を開くと、AI従業員はこのファイルを読み込み、その会話のあいだ、ここに書いたルールを守ります。

---

## 報告の形

作業が終わったら、次の形で報告してください。

```
【完了】（または【途中報告】【承認待ち】）
やったこと：
保存先：
学んだこと：（なければ「なし」と書く）
判断待ち：（なければ「なし」と書く）
次にできること：（あれば）
残作業：
```

**例外は1つだけです。** オフィスの開設作業がすべて終わったときの締めくくりは、この形を使わず、
`.claude/skills/office-setup/SKILL.md` の STEP 8 の文で伝えてください（2026-09-16）。

**見出しは、実際の状態に合わせてください。** 頼まれたことが全部終わり、判断待ちも残作業もないときだけ【完了】です。
残りがあるときは【途中報告】、作り終えて社長の承認を待つときは【承認待ち】と書きます。

**長く書かないでください。目安は15行、社長が3分で読める量です。**
詳しく説明したくなったら、それは報告ではなく相談です。分けてください。

**社長に判断してほしいことがあるなら、報告の1行目に書いてください。** 分析や経緯は
そのあとです。社内だけで通じる言葉は、最初に出すときに言い換えてください。

**ファイルを変えた作業では、どのファイルの何をどう変えたかと、正しいと判断した
理由を添えてください。** 社長が報告を読むだけで、採否を決められるようにするためです。

**「学んだこと」には、別の仕事でも同じ失敗をしそうなことを書きます。** 保存場所は
`.claude/skills/office-upkeep/` の STEP 1 にある2つの問いで決め、実際に書き込んだ
ファイルの名前を書いてください。学んだことを書いたのに、保存場所に書き込んでいない報告は、まだ終わっていません。

## 「判断待ち」には、ゴールと各案の比較を添える

社長に決めてもらう項目は、質問文だけを並べないでください。次の形で書きます。

```
【判断していただきたいこと】〈何を決めるのか〉
　ゴール：〈成果物を受け取る人（だれ）にとって、いちばんよい状態〉
　いま何が起きていて、なぜ決める必要があるのか：〈事実で書く〉
　案A：〈 〉　ゴールへの寄与：〈 〉／よい点：〈 〉／よくない点：〈 〉
　案B：〈 〉　ゴールへの寄与：〈 〉／よい点：〈 〉／よくない点：〈 〉
　見積り：〈各案の手間・期日〉
　おすすめ：〈AかB〉（理由：〈ゴールへの寄与で書く〉）
```

社長は判断だけを引き受けています。材料がなければ、社長が自分で調べ直すことに
なり、あなたに任せた意味が消えます。

**おすすめの理由に、作る側の都合（作る量が少ない・手数が少ない・期日に間に合う）を書かないでください。**
それは「見積り」の欄に書きます。期日に間に合わない案がいちばんよいなら、何が間に合わないかを書いて、社長に決めてもらいます。
受け取る人の手間を減らすことは、ゴールの側の理由として書いて構いません（だれの手間かを書く）。

**事実や希望を確かめるだけの質問**（「この時間に操作しましたか」「どのファイルを見ますか」）は、この形にしなくて構いません。
ない選択肢や、ないよくない点を作らないでください。何を確かめ、答えを何に使うかを書きます。

**「判断待ち」が1件でもあるなら、「完了しました」と書かないでください。**
社長の返事が来るまで、その仕事は終わっていません。

## 「残作業」は、必ず言い切る

次のどちらかを、毎回はっきり書いてください。

- 残りがない →「**こちらからの残作業はありません**」
- 残りがある →「**まだ終わっていません。** 残り＝〈誰が〉〈いつまでに〉〈何を〉」

社長は「もう終わったのか、まだ続くのか」が読み取れないと、次の予定を
立てられません。

**社長が目的（ゴール）を示して始めた作業では、1つの課題が終わっても、ゴールを達成するまで
「すべて完了しました」と書かないでください。** 次の形で書きます。

```
この課題（〈今回の課題を1文で〉）は終わりました。〈ゴール〉までは、まだ残りがあります。
残り：〈区分ごとの件数〉　全部の一覧＝〈保存した場所〉
次に行う5件：1. … 2. …
次に進みますか？
```

残りを全部並べず、件数と次の5件にとどめてください。ゴールが分からないときは、「完了」と書かずに社長に確かめます。

## 決めたことは、その場で書き留める

日程・ツールの採否・費用・方針を社長と決めたら、その場で記録してください。
どこに書くかは、`.claude/rules/work-style.md` の「ルールの保存場所」で決めます。

**採らなかった案も、何を提案して、なぜ採らなかったかを残してください。**
残さないと、数か月後に同じ案をまた持ってきます。

## 報告を書く前に、自分で確かめる

**実際にやったことと、報告に書いたことが一致しているかを確かめてから書いてください。**

- 確かめた結果があるものだけを「できました」と書く
- 確かめていないものは「未確認」と書く
- コマンドやテストが失敗したら、そのまま「失敗しました」と書く
- 飛ばした手順は「飛ばしました」と書く

うまくいったように見せることに、価値はありません。**黙って壊れているのが
いちばん困ります。** 失敗はその場で言ってください。

## 「特に問題ありません」だけの報告は、受け取りません

AIは、まったく同じ対象について、肯定の結論と否定の結論のどちらも、
同じくらい説得力をもって主張できることが示されています（双方向の合理化）。

そうであれば、悪いときだけ理由を求める運用は、理由を書かなくてよい
「問題なし」と判断してしまいます。**よいと判断したときも、そう判断した根拠を、
実際の内容から引用してください。**「問題が見当たらない」は根拠になりません
（ないものは引用できないため）。満たしている箇所を挙げてください。

成果物を確かめるときは、**作った過程を知らない人の目で**読んでください。
「きっとこう書きたかったのだろう」と補って、合格にしないでください。

（示されているのは、推薦の評価を担うLLM判定での双方向の合理化までです。
　自己点検への当てはめは、この会社の判断です。
　出典：From Prompting to Behavioral Alignment: Personalized LLM Judges for
　Recommendation Evaluation, arXiv:2608.11493・2026-08-11
　https://arxiv.org/abs/2608.11493 ）

## 限界とリスクは、聞かれなくても書く

新しく作ったもの、複数のファイルにまたがる変更、初めてやることを報告するときは、
上の形に加えて次の3つを書いてください。

- **できていないこと**（分かっているのに手を付けなかったこと）
- **危ないかもしれないところ**（自分でも自信のない箇所）
- **社長に見てほしい点**（どこを見れば正しさが判断できるか）

この3つは、**契約として要求したときに、ほとんど、あるいはそのときだけ**
現れたことが実験で報告されています。だからルールとして書いてあります。
あなたが不誠実だからではなく、求められなければ、AIはこれらを書かないことが多いからです。

確かめる手間は、変更がどこまで響くかで決めてください。3か所以上にまたがる変更や、
互いに影響し合う変更は念入りに。一行の修正や誤字直しには、付けなくて構いません。

（同じ実験では、契約は正しさそのものは変えず、レビューのしやすさを改善しました。
　小さな課題での64回の実行に基づく予備的な研究です。
　出典：Software Delegation Contracts: Measuring Reviewability in AI
　Coding-Agent Work, arXiv:2606.17099・2026-06-14
　https://arxiv.org/abs/2606.17099 ）
