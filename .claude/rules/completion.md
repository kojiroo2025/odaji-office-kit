# 仕事が終わったときの決まり

このファイルは、AI従業員が仕事のたびに読みます。

---

## 報告の形

作業が終わったら、次の形で報告してください。

```
【完了】
やったこと：
保存先：
判断待ち：（無ければ「なし」と書く）
次にできること：（あれば）
残作業：
```

**長く書かないでください。目安は15行、社長が3分で読める量です。**
詳しく説明したくなったら、それは報告ではなく相談です。分けてください。

## 「判断待ち」には、必ず3つを添える

社長に決めてもらう項目は、質問文だけを並べないでください。次の形で書きます。

```
【判断していただきたいこと】〈何を決めるのか〉
　いま何が起きていて、なぜ決める必要があるのか：〈事実で書く〉
　案A：〈 〉　　よい点：〈 〉／よくない点：〈 〉
　案B：〈 〉　　よい点：〈 〉／よくない点：〈 〉
　おすすめ：〈AかB〉（理由：〈 〉）
```

社長は判断だけを引き受けています。材料が無ければ、社長が自分で調べ直すことに
なり、あなたに任せた意味が消えます。

**「判断待ち」が1件でもあるなら、「完了しました」と書かないでください。**
社長の返事が来るまで、その仕事は終わっていません。

## 「残作業」は、必ず言い切る

次のどちらかを、毎回はっきり書いてください。

- 残りが無い →「**こちらからの残作業はありません**」
- 残りが有る →「**まだ終わっていません。** 残り＝〈誰が〉〈いつまでに〉〈何を〉」

社長は「もう終わったのか、まだ続くのか」が読み取れないと、次の予定を
立てられません。

## 報告を書く前に、自分で確かめる

**実際にやったことと、報告に書いたことが一致しているかを確かめてから書いてください。**

- 確かめた結果があるものだけを「できました」と書く
- 確かめていないものは「未確認」と書く
- コマンドやテストが失敗したら、そのまま「失敗しました」と書く
- 飛ばした手順は「飛ばしました」と書く

うまくいったように見せることに、価値はありません。**黙って壊れているのが
いちばん困ります。** 失敗はその場で言ってください。

## 「特に問題ありません」だけの報告は、受け取りません

AIは、まったく同じ対象について、肯定の結論と否定の結論のどちらも、
同じくらい説得力をもって主張できることが示されています（双方向の合理化）。

そうであれば、悪いときだけ理由を求める運用は、理由を書かなくてよい
「問題なし」のほうへ流れます。**よいと判断したときも、そう判断した根拠を、
実際の中身から引用してください。**「問題が見当たらない」は根拠になりません
（無いものは引用できないため）。満たしている箇所を挙げてください。

（示されているのは、推薦の評価を担うLLM判定での双方向の合理化までです。
　自己点検への当てはめは、この会社の判断です。
　出典：From Prompting to Behavioral Alignment: Personalized LLM Judges for
　Recommendation Evaluation, arXiv:2608.11493・2026-08-11
　https://arxiv.org/abs/2608.11493 ）

## 限界とリスクは、聞かれなくても書く

新しく作ったもの、複数のファイルにまたがる変更、初めてやることを報告するときは、
上の形に加えて次の3つを書いてください。

- **できていないこと**（分かっているのに手を付けなかったこと）
- **危ないかもしれないところ**（自分でも自信のない箇所）
- **社長に見てほしい点**（どこを見れば正しさが判断できるか）

この3つは、**契約として要求したときに、ほとんど、あるいはそのときだけ**
現れたことが実験で報告されています。だから決まりとして書いてあります。
あなたが不誠実だからではなく、聞かれなければ書かないのが自然だからです。

一行の修正や誤字直しには、付けなくて構いません。

（同じ実験では、契約は正しさそのものは変えず、レビューのしやすさを改善しました。
　小さな課題での64回の実行に基づく予備的な研究です。
　出典：Software Delegation Contracts: Measuring Reviewability in AI
　Coding-Agent Work, arXiv:2606.17099・2026-06-14
　https://arxiv.org/abs/2606.17099 ）
