# office-brushup（仕様からプログラムを作る・作り直す）

## 目的

このキットは、プログラムそのものではなく、**テスト付きの仕様**を配ります
（`Programs/specs/<名前>/SPEC.md` と `tests/`）。プログラムは、この会社のパソコンで、
あなたが仕様を読んで作ります。社長のパソコンの環境（Windows か Mac か、入っている言語）に
合ったものができ、仕様が新しくなっても、作り直せば追いつけます。

**作ったプログラムは、テストの材料のすべてのケースに合格するまで使い始めません。**
合格したことは、記録（`Programs/<名前>/BUILT_FROM.md`）と変更履歴（Git）に残します。
このスキルは、その「作る・試す・記録する」を毎回同じ形で行うための工程です。

## 全体に効くルール（どの STEP にも効きます）

**① 「できない」で終わらせない**

- 工夫すればでき、それが社長・会社にとってより良い結果につながると見えるなら、**必ず工夫の提案をします。**
  「できません」で終わらせません（例：仕様が求める言語がパソコンに入っていない、部品が入れられない、
  テストの1件だけがどうしても通らない）
- 提案には、①なぜいまできないか ②どう工夫すればできるか（何を入れるか・何を変えるか・費用）
  ③増える手間 ④よい点とよくない点 を添え、判断の分岐として出します。決めるのは社長です
- 本当にできないこと・してはいけないこと（安全のルールに反する、テストの期待を書き換えて通す、など）は、
  理由を添えて率直にそう言います。率直に言うことと、工夫を探すことは両立します

**② 判断を求めるときの、提案の出し方**

判断を求めるどの場面でも、次の4つをそろえます。

1. 前向きなトーンで書く
2. 必ず2つ以上の分岐を出す
3. 各案の、よい点とよくない点の両方を書く
4. おすすめと、その理由を書く（最後に決めるのは社長です）

（出どころ：`.claude/skills/skill-writing/` STEP 4「作るスキルの冒頭に、全体に効くルールを2つ書く」）

## 呼ぶタイミング

- 社長が「ブラッシュアップをしましょう」「仕組みを増やしたい」「仕様からプログラムを作って」
  「仕様が新しくなったので作り直して」と言ったとき
- 増築（`kit-update`）を終えたあと。`Programs/specs/` が変わっていたら、STEP 1 の一覧を社長に見せます
- 月に一度の見直し（`office-upkeep` の STEP 4）

## 呼ばない場面

- キットの新しいバージョンを取り込む作業そのもの → `kit-update`（取り込んだあとで、このスキルに戻ります）
- 新しい業務のスキル（仕事の手順）を作る → `skill-writing`
- ルールや記録の手入れ → `office-upkeep`
- 仕様のない、この会社だけのプログラムを書く → `program-writing`

## 任せる範囲

| 作業 | 段階 | 理由 |
|---|---|---|
| 仕様と記録を読み、一覧を作る（STEP 1） | **任せる** | 読むだけで、何も変わりません |
| どのプログラムを作るか・作り直すか（STEP 2） | **必ず社長が決める** | 使い始めるかどうかは、会社の仕事の都合で決まります |
| 外部の部品（パッケージ）や言語を入れる（STEP 2） | **必ず社長が決める** | パソコンに新しいものが入り、あとから外しにくいからです |
| 作業用のフォルダにプログラムを書く・テストを実行する（STEP 3・4） | **任せる** | 使っているプログラムには触れず、変更履歴から戻せます |
| 合格した新しい版を、使っているプログラムと入れ替える（STEP 6） | **条件つきで任せる** | 条件＝全ケース合格、経緯を知らない目の重い指摘が0件、社長が書き換えた箇所がない（あるときは STEP 3 で社長が決めた方針どおり）。条件の外は社長に聞きます |
| 社長が書き換えたプログラムを作り直す（STEP 3） | **必ず社長が決める** | 社長の工夫を消すおそれがあるからです |
| 合格しないケースの扱い（STEP 4） | **必ず社長が決める** | 期待を書き換えて通すことは、どの段階でもしません |
| 変更履歴（Git）への記録（STEP 6） | **任せる** | 記録は、戻れるようにするための操作です |

## STEP 1　仕様と、作ったプログラムを見比べる

1. `Programs/specs/README.md`（仕様の一覧）と、`Programs/specs/` の下のフォルダを全部読みます。
   一覧とフォルダの数が合わないときは、そのことも社長に伝えます
2. 仕様ごとに、`SPEC.md` の「仕様のバージョン：N」と、`SPEC.md`・`tests/cases.json` の指紋（SHA-256）を控えます
3. 同じ名前の `Programs/<名前>/BUILT_FROM.md` があれば読み、元にした仕様のバージョン・指紋・
   プログラムのファイルの指紋と比べます
4. 次の表で分け、社長に一覧で見せます

| 分類 | 見分け方 |
|---|---|
| まだ作っていない | 仕様はあるが、`Programs/<名前>/` がない |
| 記録がない | `Programs/<名前>/` はあるが、`BUILT_FROM.md` がない（前のバージョンのキットに入っていたプログラム、社長が作ったもの） |
| 仕様が新しくなった | 仕様のバージョンが記録より大きい。**または、バージョンは同じでも `SPEC.md`・`cases.json` の指紋が記録と違う** |
| 書き換えられている | プログラムのファイルの指紋が、記録と違う（ほかの分類と重なることがあります） |
| 最新 | 仕様のバージョン・指紋・プログラムの指紋が、すべて記録と同じ |
| 仕様がなくなった | `BUILT_FROM.md` はあるが、元の仕様が `Programs/specs/` にない |

指紋の取り方（どちらも、ファイルの中身から決まる64文字の英数字が出ます。Windows の PowerShell は英字を大文字で、Mac は小文字で出すので、比べるときは大文字と小文字をそろえます）：

```powershell
# Windows（PowerShell）
Get-FileHash -Algorithm SHA256 .\Programs\specs\<名前>\SPEC.md
```

```bash
# Mac（ターミナル）
shasum -a 256 Programs/specs/<名前>/SPEC.md
```

見せる形：

```
仕様とプログラムを見比べました（仕様 〈N〉件）。

| 名前 | 分類 | 仕様のバージョン（記録→いま） | 何をするプログラムか |
|---|---|---|---|
| 〈名前〉 | まだ作っていない | なし→2 | 〈SPEC.md の目的を1文で〉 |
| …

「記録がない」「書き換えられている」「仕様がなくなった」は、作り直す前に社長に確かめます（STEP 2）。
```

- **「仕様がなくなった」プログラムは、消しません。** 使い続けるか・やめるかを社長に聞きます
- 「最新」だけのときも、月に一度の見直しでは「テストだけもう一度実行しますか」と聞きます。
  パソコンの言語や部品が更新されて、同じプログラムが通らなくなることがあるからです
- 仕様のファイルは、キットのファイルです。**仕様の文やテストの材料を、あなたが書き換えないでください。**
  書き換えると、次の増築で社長の書き換えと見分けがつかなくなり、合格の意味もなくなります

## STEP 2　作るものを、社長に選んでいただく

一覧から、作る・作り直すものを社長に選んでいただきます。**1回に1つずつ**作ります
（並べて作ると、どのテストがどのプログラムの結果かが混ざります）。

選ばれたものについて、作る前に次を確かめて社長に見せます。

1. **仕様が求める言語と外部の部品。** `SPEC.md` に書いてある言語・部品が、このパソコンにあるかを確かめます
   （Windows は `py --version` または `python --version`、Mac は `python3 --version` など）
2. **入れるものがあるとき**は、`.claude/skills/program-writing/` STEP 1 の「部品を新しく入れるとき」の確かめ方
   （公式のページ・利用者の多さ・最近の更新・保守している人の数）で調べ、**部品の名前・バージョン・入れ方・
   入れると何が増えるか**を1つずつ見せて、承認を得てから入れます
3. 言語が入っていない、部品が入れられないときは、「できない」で終わらせず、分岐を出します
   （例：案A＝言語を入れる／案B＝部品を使わない書き方で作る（仕様が許すとき）／案C＝今回は作らない）
4. 「記録がない」ものは、いまのプログラムを残すか、仕様から作り直すかを聞きます。
   作り直すときは、いまのプログラムも STEP 4 のテストに一度かけ、結果を並べて見せます
5. 「書き換えられている」ものは、STEP 3 の「社長が書き換えたプログラム」の手順で進めます

## STEP 3　プログラムを書く

`.claude/skills/program-writing/` を読み、その手順（書く前・書くときの作法・書いたあとで）で書きます。
このスキルでは、次を加えます。

- **書く場所は、作業用のフォルダ `Programs/<名前>/_next/` です。** 使っているプログラム（`Programs/<名前>/` の直下）は、
  新しい版が全ケースに合格して入れ替えるまで、そのまま使える状態に残します
- 仕様に書いていないふるまいを足さないでください。足したほうがよいと思ったら、提案として社長に出します
- **テストの材料のファイル名や中身を見て、答えを決め打ちする書き方をしないでください**
  （例：特定のファイル名のときだけ決まった文を出す）。テストには通っても、実際のファイルでは動きません
- 書いたら、**どう起動するか**（例：`python Programs/<名前>/_next/<ファイル> 〈引数〉`）を決めて控えます。
  STEP 4 のテストと、STEP 6 の記録で使います

### 社長が書き換えたプログラム

社長（または社長の頼みで別の会話）が書き換えたプログラムを、**作り直しで上書きしないでください。**

1. 前に記録したときから何が変わったかを、変更履歴（Git）で見て、社長に見せます

   ```
   git log -1 --format=%H -- Programs/<名前>/BUILT_FROM.md
   git diff 〈前の行で出た英数字〉 -- Programs/<名前>
   ```

2. 次の分岐で、社長に決めていただきます

   - 案A：新しい仕様で作り直し、社長の書き換えを、新しい版にも入れる（入れた箇所を見せ、テストにも通す）
   - 案B：新しい仕様で作り直し、社長の書き換えは入れない（いまの版を `Programs/<名前>/_before_<日付>/` に写して残す）
   - 案C：作り直さず、いまの版を使い続ける（仕様の新しいところは入りません。記録に「作り直さなかった」と書きます）

   よい点・よくない点・おすすめは、書き換えの中身を見て書きます。書き換えが、新しい仕様で直された点と同じ
   ものなら、案Bでも失うものがないことがあります

## STEP 4　テストの材料の全ケースを実行する

`Programs/specs/<名前>/tests/cases.json` のケースを、**1件残らず**実行します。
`cases.json` の欄の意味と、実行と判定の決まりの正本は、`Programs/specs/README.md` の「テストの実行の決まり」です。
下の手順と食い違うときは、そちらに従います。

### 1件の実行のしかた

1. 空の一時フォルダを、ケースごとに新しく作ります（前のケースの残りを使わないため）
2. `args` の中の `{fixtures}` を `Programs/specs/<名前>/tests/fixtures` の絶対パスに、`{tmp}` を作った一時フォルダの
   絶対パスに置き換えます。パスに空白があっても1つの引数として渡します（コマンドの文字をつなげて作らず、
   引数を1つずつ渡します）
3. 作業フォルダを `{tmp}` にして（相対パスで書くプログラムが、AIオフィスのフォルダに書き込まないため）、
   STEP 3 で決めた起動のしかたで、置き換えた `args` を渡して実行します。1件の制限時間は 60 秒です。
   超えたら止めて、合格にしません
4. 終了コードと、標準出力（画面に出る文字）を受け取ります。標準出力は UTF-8 として読み、
   先頭の目に見えない印（BOM）を除き、改行の違い（CRLF と LF）をそろえてから比べます。
   エラー出力も記録します（判定に使うのは、`expect_output_hides_line` の確認だけです）
5. 次を比べ、**全部が合ったときだけ合格**にします
   - `expect_exit`：終了コードが同じか
   - `expect_stdout_contains`：並んだ文字列が、**どれも**標準出力に含まれているか
   - `expect_stdout_not_contains`：並んだ文字列が、**どれも**標準出力に含まれていないか
   - ケースによって付いている次の4つも、**付いていれば必ず**確認します（読み飛ばすと、ファイルを残す・パスワードを
     画面に出す、といった誤りを見ないまま合格にしてしまいます）
     - `setup_dirs`：実行の前に、`{tmp}` の下にそのフォルダを作っておく
     - `expect_exists`：実行のあとに、そのパスがあるか（ファイルでもフォルダでもよい）
     - `expect_not_exists`：実行のあとに、そのパスがないか（ファイルでもフォルダでも、あれば不合格）
     - `expect_output_hides_line`：指定したファイルの指定した行（パスワードなど）が、標準出力にもエラー出力にも出ていないか
     - `expect_file_contains`・`expect_file_differs`・`expect_file_line_matches`・`expect_pdf_password`：ファイルの中身が決めたとおりか
       （意味は `Programs/specs/README.md`。パスワードの行が合わなかったときも、その行の文字を報告に写しません）
   - 実行のあとの `{tmp}` に、`expect_exists` のパス（と、その下）のほかに、ファイルが残っていないか（空のフォルダは問いません）
   - 知らない欄・同じ欄が2つ・空の語・`null` の欄があったら、合格にせず、社長に知らせます（自分の判断で合格にしません）
6. **全ケースの前と後で、`Programs/specs` フォルダ全体のファイルの指紋を比べます。**
   変わっていたら、プログラムが仕様のフォルダに書き込んでいます。不合格にし、キットの元のファイルから戻してから続けます

### テストを実行するツール

ケースは仕様ごとに数十件あるので、手で1件ずつ比べず、上の手順を行う小さなテストを実行するツールを
`Programs/brushup-runner/` に1つ作り、どの仕様にも使い回します（書き方は `program-writing`。月に一度の見直しでも使います）。

**作ったら、使う前に、わざと失敗させた次の16通りを作業用の写しで与え、どれにもツールが「不合格」（または「判定できない」）と言うことを確認します。**
不合格を言えないツールは、偽の合格を出します。1つでも「合格」と言ったら、ツールを直してから、16通りをもう一度与えます。

1. 終了コードが期待と違う
2. `expect_stdout_contains` の語が、標準出力にない
3. `expect_stdout_not_contains` の語が、標準出力にある
4. `expect_exists` のパスがない
5. `expect_not_exists` のパス（フォルダの場合も試す）がある
6. `expect_output_hides_line` の行の文字が、標準エラーにだけ出ている
7. 仕様のフォルダ（`fixtures` の隣の `cases.json` を含む）に、プログラムが書き込んだ
8. `{tmp}` に、書きかけのファイルが残った
9. `cases.json` に、知らない欄がある
10. `cases.json` に、同じ欄が2つある・空の語がある・`null` の欄がある
11. `expect_output_hides_line` のファイルがない、またはその行が空
12. 制限時間（60秒）を超える
13. `setup_dirs` が `{tmp}` の外を指している
14. `expect_file_contains` の文字がファイルにない／`expect_file_differs` の2つが同じバイト
15. `expect_file_line_matches` の行が正規表現に合わない
16. `expect_pdf_password` の PDF が、空のパスワードで開ける（または、保存したパスワードで開けない）

わざと失敗させるには、引数どおりに動く小さな作り物のプログラムを作業用のフォルダに作り、それをツールにかけます
（作ったプログラム・キットの `cases.json` は書き換えません）。

- Windows では PowerShell、Mac ではターミナルから実行します。Python のツールなら、Windows は `py` か `python`、
  Mac は `python3` で起動します
- 文字化けしたら、まず読み方（文字コード）を疑い、プログラムとテストの両方で UTF-8 を指定します

### 結果の表

```
| id | 結果 | 終了コード（期待→実際） | 合わなかった文字列 | note |
|---|---|---|---|---|
| 〈id〉 | 合格 | 1→1 | なし | 〈cases.json の note〉 |
| 〈id〉 | 不合格 | 0→2 | 「〈文字列〉」が出ていない | … |

全 〈N〉 件中 〈M〉 件合格
```

### 合格しないケースがあったとき

- プログラムを直して、**全ケースをもう一度**実行します（直したケースだけを実行しません。ほかのケースが壊れることがあります）
- **合格しないケースを、期待のほう（`cases.json`・テストの材料・比べ方）を書き換えて通さないでください。**
  あなたが「テストのほうが間違っている」と思ったときも同じです。その理由と根拠を社長に見せ、
  分岐を出して決めていただきます（例：案A＝このケースは不合格のまま、使い始めない／案B＝キットの作り手に
  知らせ、次のバージョンを待つ）
- 3回直しても通らないときは、いったん止めて、何が通らないかと、試したことを社長に報告します
- **1件でも不合格が残っているあいだは、使い始めません。** 入れ替え（STEP 6）にも進みません

## STEP 5　経緯を知らない目に、偽の合格を探させる

全ケースに合格したら、作った過程を知らない別のAI（サブエージェント）に確かめさせます。
自分の作ったものを自分で確かめると、甘くなるからです。

渡すもの：`SPEC.md` の全文・`cases.json` の全文・`_next/` のプログラムの全文（要約しない）・
STEP 4 の結果の表・テストを実行するツールを使ったなら、そのツールの全文。**あなたの結論（「全部合格しました」「問題ないはずです」）は渡しません。**

挙げてもらうもの（放っておくと被害が出るものだけ）：

1. **偽の合格**：テストの材料の名前や中身で答えを決め打ちしている／比べ方が甘く、失敗しても合格に見える／
   仕様にあるのにテストがないふるまいを、プログラムが満たしていない
2. **失敗の握りつぶし**：読めなかった・壊れたファイルを「問題なし」と扱う／エラーを捕まえて終了コード 0 で終える
3. **上書き**：テストの材料・一時フォルダの外・使っているファイルを書き換える／消す

- 指摘を直したら、STEP 4 の全ケースをもう一度実行し、**直した版を、もう一度経緯を知らない目に読ませます**
  （直すときに、新しい偽の合格が入ることがあります。`program-writing` STEP 3）。重い指摘が出なくなるまで繰り返します
- 「問題なし」が返ってきたら、それを正常な結果として受け取ります
- 呼び出せなかったときは、**黙って自分で代わりにやらないでください。** 「呼び出せませんでした」と社長に伝えます

## STEP 6　入れ替えて、記録する

1. `_next/` の中身を `Programs/<名前>/` の直下へ写し、入れ替えます（「書き換えられている」ものは、STEP 3 で社長が決めた案のとおり）
2. 入れ替えたあと、`Programs/<名前>/` の直下のプログラムで、STEP 4 の全ケースを**もう一度**実行します。
   写すときの取り違えを見つけるためです
3. `_next/` を消します。消せない設定になっているときは、社長に消していただきます
4. `Programs/<名前>/BUILT_FROM.md` を書きます（下の形）
5. `Programs/README.md` の一覧と `CLAUDE.md` に、プログラムの場所と何をするものかを書き足します
   （`Programs/README.md` の、このフォルダにプログラムを作ったときの決まり）。入れた部品は、名前とバージョンを `Programs/README.md` に書きます
6. 変更履歴（Git）に記録します。**変えたファイルを名指しして記録します**（全部をまとめて記録しない）。
   記録する前に、変わった行数を見ます（`git diff --stat`）。1行の直しで全部の行が変わっていたら、改行の種類が変わっている可能性が高いので、`git diff --ignore-cr-at-eol --stat` で、改行の違いを除いた行数を確認します

`BUILT_FROM.md` の形：

```
# このプログラムを作った元

- 仕様：Programs/specs/〈名前〉/SPEC.md
- 仕様のバージョン：〈N〉
- 仕様の指紋（SHA-256）：SPEC.md 〈64文字〉／tests/cases.json 〈64文字〉
- 作った日：〈YYYY-MM-DD〉
- 起動のしかた：〈例：python Programs/〈名前〉/〈ファイル〉 〈引数〉（Mac は python3）〉
- 言語とバージョン：〈例：Python 3.12.4〉
- 入れた部品：〈なし／名前とバージョン〉
- テストの結果：全 〈N〉 件中 〈N〉 件合格（実行した日 〈YYYY-MM-DD〉・入れ替えたあとの版で実行）
- プログラムのファイルの指紋（SHA-256）：〈ファイル名〉 〈64文字〉（ファイルごとに1行）
- 経緯を知らない目の確認：〈日付〉・指摘〈N〉件・直したもの〈…〉
- 社長が書き換えた箇所の扱い：〈なし／案A・B・C のどれか〉
```

**作り直さなかった・作るのをやめたときも、`BUILT_FROM.md` に理由を1行書きます**（STEP 3 の案C、STEP 4 で使い始めないと決めたとき）。
書かないと、次の見直しで同じことをもう一度聞くことになります。

## STEP 7　報告する

`.claude/rules/completion.md` の形で報告し、次を添えてください。

- 作った・作り直したプログラムの名前と場所、元にした仕様のバージョン
- STEP 4 の結果の表（入れ替えたあとの実行の結果）
- 経緯を知らない目の指摘と、直したもの。呼び出せなかったら、そう書く
- 入れた部品（名前・バージョン）
- 作らなかったもの・作り直さなかったものと、その理由
- STEP 1 の一覧で、まだ残っているもの（「まだ作っていない」「仕様が新しくなった」の件数）

最後に、こう伝えて終えます。

> 必要なら、いつでも壁打ちやブラッシュアップができるので、声をかけてください。

## 気をつけること

- **終了コード 0 が出たことや、エラーが出ないことは、合格の証拠になりません。** `cases.json` の期待と比べた結果だけが証拠です
- **ケースの一部だけを実行して「合格」と書かないでください。** 結果の表の件数が、`cases.json` のケースの数と同じかを確かめてから報告します
- 仕様の文と、テストの期待が食い違って見えるときは、どちらかに合わせて黙って進めず、社長に見せます
- 本番のデータ（社長の実際のファイル）でテストしないでください。テストは `fixtures` と `{tmp}` だけで行います
