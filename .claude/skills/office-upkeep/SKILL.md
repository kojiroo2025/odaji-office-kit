# office-upkeep（ルールの手入れ）

## 目的

ルールと記録は、**増えるほど読まれなくなり、古くなるほど間違いを生みます。**
同じことが2か所に書かれていれば、いずれ片方だけが直されて食い違います。

このスキルは、ルールと記録を、増やすときも減らすときも、
読まれる形のまま保つための手入れです。

## 呼ぶタイミング

- ルールを書き足す・直すとき（STEP 1）
- フォルダやファイルを足す・移動するとき（STEP 2）
- 記録を消す・整理するとき（STEP 3）
- 月に一度・3か月に一度の見直し（STEP 4・STEP 5）
- 社長から同じ指摘を2回受けたとき（STEP 1）

## 呼ばない場面

- 新しいAI従業員（スキル）を作る → `skill-writing`
- 開設の続き → `office-setup`

## STEP 1　ルールを足すとき

保存場所は `.claude/rules/work-style.md`「ルールの保存場所」の表で決めます。そのうえで：

- **そのルールが守られているかを、文字の有無や実行した結果で機械が判定できるなら、
  ルールを書く前に、確かめる仕組み（小さな確認プログラム）をあなたが作ってください。**
  たとえば「ファイル名は日付で始める」なら、日付で始まっていないファイルを探す
  確認を用意できます。仕組みは読まれなくても働きますが、ルールは読まれないと
  働きません。両方置いても構いません（仕組みは「破れたら知らせる」、ルールは
  「なぜそうするか」を伝える）
  - **その確認プログラムを書く前に、`.claude/skills/program-writing/` を読んでください。**
    **確認するだけのプログラムでも、書くことに変わりはありません。**
    鍵の扱い・文字コード・試し方・社長への見せ方は、そちらに書いてあります
- 「必要なら確認する」「分かっているなら省く」のような条件を書くときは、何をもって
  必要・分かっているとするかも書いてください。「省いてよい」とだけ書くと、確かめる
  べき前提を、あとのあなたが推測で決めてしまいます
- 外の記事や別のAIから「この仕組みを入れよう」という提案が来たら、提案をそのまま
  入れず、その提案が防ごうとしている穴を見つけて、その穴を塞ぐ形で足してください。
  出典があれば、その記事が実在するか・いつ・だれが書いたかを元のページで確かめ、
  採った部分と採らなかった部分を、理由とともに記録します。この会社の規模に合わない
  仕組み（専任の担当や別のシステムが要るもの）は、考え方だけを採ります
- 社長からの提案は、そのまま入れてください。ただし、その提案が防ごうとしている穴を
  1文で確かめ、別の形のほうがその穴を塞げると思うときは、案を添えて社長に決めて
  もらいます
- **同じルールを2か所に書かないでください。** 2か所目が要るときは、
  「〇〇を見てください」とだけ書きます
- **いつもの確認を省く例外**（「この作業は確認なしで進めてよい」）を作るときは、
  省いてよい前提（外に出ない、元に戻せる、など）と一緒に書いてください。
  対象を足したら、例外の一覧も同時に直します。前提と対象が食い違うと、
  ルールは守られなくなります
- ルールを直したら、**日付と理由を**書き残してください。「こういう傾向が
  見られた」という観察と、「こうする」というルールは、分けて書きます
  （観察をルールとして扱うと、文章や仕事が型にはまっていきます）
- 仕事の中で学んだことは、次の2つを自分に問うてから保存場所を決めます
  1. これを知らない自分は、別の仕事でも同じ失敗をするか → するなら、その仕事だけの話ではない
  2. 次に同じ場面に来た自分は、これを探そうと思いつくか → 思いつかないなら、
     **毎回読み込まれる場所**（`.claude/rules/`・`CLAUDE.md`）に置く。
     知らないことは、探しようがありません

## STEP 2　フォルダやファイルを足す・移動するとき

- 新しいフォルダを変更履歴（Git）に載せるかは、3つの問いで決めます
  1. 人が書いたり直したりするものか（機械が作るものではないか）
  2. 文字のファイルか（違いを読めるか）
  3. 上書きや削除から戻す手段が、ほかにないか

  **3つとも「はい」なら載せます。** 載せないフォルダは、今日の変更がバックアップ
  でしか戻らない（＝今日の分は戻らない）ことを、社長に伝えてください
- 変更履歴があるかどうかは、**そのフォルダそのもの**で確かめてください。
  親のフォルダで確かめて「ない」と判断しないでください。変更履歴の中に、
  別の変更履歴を作らないでください（下の変更履歴が見えなくなります）
- ほかのルールやファイルから参照されている**名前や番号は、変えないでください。**
  移動するときは、名前を変えず、同じファイルを2か所に置かず、一度に移し終えます
  （コピーしてあとで消す、をしない）
- 見本やテンプレートのファイル名を、**本番の設定ファイルと同じ名前にしないでください。**
  取り違えが起きます
- 「全部のファイルに入れた」と記録する前に、**全部を検索して確かめてください。**
  覚えている範囲で「済」と書かないでください

## STEP 3　記録を消す・整理するとき

- 「古い」「使われていない」だけで消さないでください。消してよいのは、次のどれかです
  1. その記録が扱っていた仕組みが、止まっている
  2. その仕事が終わり、学んだことが上のルールへ移っている
  3. 「未着手」と書いてあるのに、残っている仕事の一覧にない

  ただし、**止まった仕事の記録ほど、ほかのどこにもない教訓や、再開するときの
  宿題が残っていることがあります。** 内容を読むまで決めないでください
- 残っている仕事は、**1枚の表にまとめてください。** 仕事ごとに進捗の
  ファイルを作ると、全体が見えなくなり、更新も漏れます
- 「今は決めない」「あとで考える」と決めたことも、同じ表に1行で置きます。
  書く欄は、何を・なぜ今は決めないのか・いつ（何が起きたら）見直すか・
  詳しい記録の場所・書いた日、の5つです。**見直す条件のない保留は、忘れられます**
- 手順をやめたら、その手順に関係する**残っている仕事も消してください。**
  終わらせようのない仕事は、次に読む人を間違った手順へ連れていきます

## STEP 4　月に一度の見直し

月に一度は「運用の記録から、小さく直す」回です。**消すのは提案まで**にして、
まとめる・構成を変えるのは3か月に一度の回に回します。

1. **社長の訂正の言葉を振り返る。** 「違う」「勝手に」「何度も言っている」と
   言われた場面を見直し、同じ指摘が2回以上あれば、ルールにします
2. **手順書が「正本」と名指ししているファイルが、いまも正本かを確かめる。**
   更新の止まったファイルを、正本と書いたままになっていることがあります
3. **同じ一覧が複数の場所に書かれていないかを、検索で全部のファイルを調べて探す**
   （目で読むと見落とします）。片方だけ古くなっていたら、1か所にまとめます。
   見つかった件数の多い少ないで良し悪しを決めず、1件ずつ内容を見ます
4. **学んだことが、毎回読み込まれる場所に上がっているかを見る。** 気づいた瞬間に
   上げ忘れたものを、ここで拾います
5. **既にあるルールに「必要なら」「分かっているなら」のような条件が残っていないかを
   見る。** 残っていたら、何をもって必要・分かっているとするかを書き足します
6. **保留（「今は決めない」と決めたこと）の行を全部読み、見直す条件が来ているものを
   社長に出す。** 見直す条件が書かれていない保留があれば、その場で条件を決めます
7. **何も見つからなかった回も、「なし」と書いて閉じる。** 書かずに飛ばすと、
   見直したのか、忘れたのかが区別できなくなります

## STEP 5　3か月に一度の点検

足すときの点検だけでは、**足したあとで要らなくなった権限**には気づけません。

- つながっているサービス、鍵の名前（値は見ない）、渡している権限、許可の一覧を、
  実際に数えてください。使っていないつながりや、広すぎる権限を見つけたら、
  外すことを社長に提案します。**増える一方で減る道のない一覧**は、機械で数えます
- 次の4つの被害と5つの入口で、いまの仕組みを見直してください

| 4つの被害 | 5つの入口 |
|---|---|
| 意図しない操作をされる | 外の情報源（メール・ウェブ） |
| 仕事を邪魔される・止められる | AIが覚えていること（メモリ） |
| 社内の情報が漏れる | つないだツールや部品 |
| 使いすぎて費用や資源を食う | 利用者からの入力 |
| | ツールからツールへの受け渡し |

- いま動いている自動の処理とつなぎ先を全部並べ、`.claude/rules/safety.md`
  「外の文章をAIに読ませる仕組みを作る前に」の3つ（外の文章を読む・社内の秘密に
  触れる・外へ送る）がそろっているものがないかを見てください。1つもなければ、
  「該当なし」と1行書きます。3か月に一度にしているのは、自動の処理を足す回数が
  少ない会社を想定しているためです。月に何度も足す会社では、この点検を月に一度に
  してください
- 「リンクを知っている人なら誰でも見られる」形で共有しているファイル・ページを数え、
  要らなくなったものは、社長に確認してから共有をやめます
- Claude Code の変更履歴（https://code.claude.com/docs/en/changelog 。Claude Code の
  中で `/release-notes` と打っても見られます）を読み、社長に確認を求める範囲の
  既定が変わっていないかを見てください。変わっていたら、社長の `settings.json` で
  その項目が決めてあるか、既定のままかを実際に開いて確かめ、社長に伝えます

## 社長の文章のくせを集めて書き足す（進捗の表の㉓）

**急ぎません。書かせてみてからでないと、正解が決まりません。**

**始めてよい合図は1つです。**

> **社長が、あなたの書いた文章を直した回数が、5回を超えたとき。**
> （または社長が「私らしい書き方を覚えて」と言ったとき）

**5回に満たないうちは、㉓は「未」のままにしてください。**
早く聞いても、社長は答えられません。**書かせてみてから足すのが確実です。**

### やり方

1. **社長が直した箇所を、直す前と直したあとで並べてください**（5件以上）
2. **そこから、繰り返し出ている型を3つまで取り出します**
   （例：「〜させていただきます」を「〜します」に直された、が3回）
3. **社長に見せて、確かめます**

```
これまでに社長が私の文章を直してくださった箇所を見返すと、
次の3つの直し方が、繰り返し出ていました。
これを「社長の文章の書き方」として覚えておいてよろしいですか。
違うものがあれば、その番号を教えてください。

1. 〈直す前〉→〈直したあと〉（〈N〉回）
2. …
3. …
```

4. **社長が「はい」と言ったものだけ**を、`Shared_Assets/Japanese_Writing_Rules.md` の
   **④「あなたの名前の書き方」**の欄に書きます
5. **`SETUP_STATUS.md` の㉓を「済」にします**

**あなたの推測で足さないでください。** 直された回数という**数えられる証拠**が要ります。

## 報告

`.claude/rules/completion.md` の形で報告し、次を添えてください。

- 足した・直した・消したルールと記録（どのファイルの、どこか）
- 消すことを提案したもの（消すかどうかは社長が決めます）
