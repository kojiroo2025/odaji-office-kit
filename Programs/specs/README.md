# プログラムの仕様（`Programs/specs` フォルダ）

このフォルダには、**プログラムそのものは入っていません。入っているのは、テスト付きの仕様です。**

パソコンの環境（Windows か Mac か・入っている Python のバージョンなど）は、会社ごとに違います。
できあがったプログラムを配ると、環境の違いで動かないことがあります。
そこで、**社長のパソコンの Claude Code が、仕様を読んでプログラムを作り、
テストの材料のすべてのケースに合格してから使い始める**形にしています。

---

## 仕様の一覧

| 名前 | 何をするか | いつ使うか | 仕様のバージョン | 外部の部品 |
|---|---|---|---|---|
| `xlsx-check` | プログラムで作った Excel のファイルに、開いたときに Excel が修復を求める原因がないかを検査する | `.xlsx` を作らせた・書き換えさせた直後 | 1 | 要りません |
| `docx-md-match` | 原稿（`.md`）から作った Word の本文が、原稿と同じ文かを照合する | 原稿から Word を作った直後 | 1 | 要りません |
| `skill-listing-check` | スキルの説明が、Claude Code に届いているかを検査する | スキルを足したあと・月に1回の見直し | 1 | 要りません |
| `pdf-encrypt` | PDF に、開くためのパスワード（AES-256）を付けた写しを作る | PDF を社外へ送る前 | 1 | **要ります**（`pypdf`・`cryptography`。入れる前に社長の承認を得ます） |

どの仕様のプログラムも、**終了コード 0 だけが合格**です。
1 は「問題あり」、2 は「読めなかった・判定できない・引数の誤り」で、2 は検査できていないので、合格として扱いません。

## 使い方

Claude Code に、次のように伝えてください。

```
ブラッシュアップをしましょう
```

Claude Code が、スキル `office-brushup`（`.claude/skills/office-brushup/`）の手順に従って、
仕様を読み、プログラムを `Programs/<名前>/` に作り、テストの材料で試します。
`pdf-encrypt` のように外部の部品が要るものは、入れる前に社長に確認します。

1つだけ作りたいときは、「`Programs/specs/xlsx-check/SPEC.md` の仕様で、プログラムを作ってテストして」
のように、仕様の名前を伝えてください。

## フォルダの中身

```
Programs/specs/
├── README.md                 この文書
└── <名前>/
    ├── SPEC.md               仕様（目的・呼び出し方・判定の規則・終了コード・やってはいけないこと など）
    └── tests/
        ├── cases.json        テストのケースの一覧
        └── fixtures/         テストの材料（入力のファイル。合格するはず・不合格になるはず・読めないはず の3種）
```

作ったプログラムは、`Programs/<名前>/` に置きます（このフォルダの中には置きません）。
**`SPEC.md`・`cases.json`・`fixtures/` は、書き換えないでください。**
合格しないケースがあるときに直すのは、プログラムの側です。

## テストの実行の決まり（Claude Code へ）

### `cases.json` の形

配列です。1つの要素が、1つのケースです。

```json
{
  "id": "bad_cols",
  "args": ["{fixtures}/bad_cols.xlsx"],
  "expect_exit": 1,
  "expect_stdout_contains": ["問題 1 件", "別表", "C-1", "F〜G"],
  "expect_stdout_not_contains": ["問題なし"],
  "note": "列の定義 F〜G と G が重なっている"
}
```

| 欄 | 意味 |
|---|---|
| `id` | ケースの名前（仕様の中で重ならない） |
| `args` | プログラムに渡す引数。この順に、1つずつ別の引数として渡す（1つの文字列につなげない） |
| `expect_exit` | 期待する終了コード |
| `expect_stdout_contains` | 標準出力に、すべて含まれているはずの語 |
| `expect_stdout_not_contains` | 標準出力に、1つも含まれていないはずの語 |
| `note` | 何を見るケースか |

次の8つは、あるケースにだけ付いています（いまは `pdf-encrypt` だけ）。**付いているケースでは、必ず確認してください。**

| 欄 | 意味 |
|---|---|
| `setup_dirs` | プログラムを実行する前に作っておくフォルダ（`{tmp}` の下だけ） |
| `expect_exists` | 実行のあとに、あるはずのパス（ファイルでもフォルダでもよい） |
| `expect_not_exists` | 実行のあとに、ないはずのパス（ファイルでもフォルダでも、あれば不合格） |
| `expect_output_hides_line` | `{"file": パス, "line": 行番号}`。実行のあとに、そのファイルのその行（1行目から数える）を読み、**その文字が、標準出力にも標準エラーにも出ていないこと**を確認する。ファイルがない・その行が空なら、不合格 |
| `expect_file_contains` | `[{"file": パス, "text": 文字}]`。そのファイルのバイトの中に、その文字（UTF-8）が含まれていること（例：出力の PDF に、暗号の辞書の印 `/Encrypt` と AES-256 の印 `/AESV3` がある） |
| `expect_file_differs` | `[{"file": パス, "other": パス}]`。2つのファイルが、同じバイトではないこと（例：出力の PDF が、元の PDF をそのまま写したものではない）。どちらかが読めなければ、不合格 |
| `expect_file_line_matches` | `[{"file": パス, "line": 行番号, "pattern": 正規表現}]`。その行の全体が、その正規表現に合うこと（例：パスワードの行が、決めた16字の形）。**合わなかったときも、その行の文字は報告に写さない** |
| `expect_pdf_password` | `{"pdf": パス, "password_file": パス, "line": 行番号, "pages": 数}`。その PDF を開いて、**空のパスワードでは開けない**こと、`password_file` のその行のパスワードで**開ける**こと、暗号の方式が AES-256（`/V` 5・`/R` 6）であること、ページ数が `pages` と同じことを確認する。PDF を開くには pypdf が要る（`pdf-encrypt` を作るときに入れたもの）。pypdf がなければ、合格にしない。**パスワードの文字は報告に写さない** |

### 置き換える文字

`args` と、パスを書く欄の中の次の文字を、実行の前に置き換えます。

| 文字 | 置き換えるもの |
|---|---|
| `{fixtures}` | その仕様の `tests/fixtures` フォルダの絶対パス |
| `{tmp}` | **ケースごとに新しく作る、空の一時フォルダ**の絶対パス。ケースが終わったら、そのフォルダだけを消す。**パソコンの一時フォルダ（プログラムの言語の機能で調べる。Windows では利用者のフォルダの中）の下に作ります。AIオフィスの中には作りません**（pdf-encrypt は、Windows で利用者のフォルダの外にパスワードを書くことを拒むため） |

### 実行と判定

1. ケースごとに、空の一時フォルダを作り、`setup_dirs` があればそのフォルダを作る
2. 作業フォルダを `{tmp}` にして、プログラムを `args` で実行する。標準出力と標準エラーを、UTF-8 として別々に受け取る。
   1件の制限時間は 60 秒。超えたら止めて、合格にしない
3. 次のすべてに当てはまれば、そのケースは合格
   - 終了コードが `expect_exit` と同じ
   - 標準出力に、`expect_stdout_contains` の語がすべてある
   - 標準出力に、`expect_stdout_not_contains` の語が1つもない
   - 上の8つの欄があれば、そのとおりである
   - 実行のあとの `{tmp}` の中に、`expect_exists` のパス（と、その下）のほかに、ファイルが残っていない
     （書きかけのファイル・別の名前の写しを残すプログラムを、合格にしないため。空のフォルダは問わない）
   - `cases.json` の形が正しい（知らない欄・同じ欄が2つある・空の語・`null` の欄は、合格にせず、社長に知らせる）
4. **全ケースの前と後で、`Programs/specs` フォルダ全体（どの仕様の `SPEC.md`・`tests/cases.json`・`tests/fixtures` も）の中身が
   変わっていないこと**を確認する（ファイルの一覧と中身のハッシュを比べる）。変わっていたら、プログラムが仕様の
   フォルダに書き込んでいるので、不合格
5. **全ケースに合格するまで、プログラムを使い始めない。** 合格の数と、不合格のケースの `id` を、社長に報告する

### 気をつけること

- `expect_output_hides_line` のあるケースは、パスワードを扱います。
  **そのケースの出力と、そのファイルの中身を、会話や記録に写さないでください**（不合格のときも、「出ていた」という事実だけを報告します）
- ケースを1件ずつ手で実行して目で比べるのではなく、`cases.json` を読んで全ケースを実行する小さなプログラム
  （テストを実行するツール）を作って、機械で比べてください。仕様を作り直すたび・月に一度の見直しのたびに使うので、
  `Programs/brushup-runner/` に置いて使い回します。作り方と、使う前に「不合格」と言えるかを確認する手順は、
  `.claude/skills/office-brushup/SKILL.md` の STEP 4 にあります
- `cases.json` に、ここに書いていない欄があったら、黙って無視せず、社長に知らせてください
  （仕様が新しくなっていて、見るべき期待が増えているかもしれません）
- テストの材料の中には、わざと壊してあるファイル・`.jsonl` や `SKILL.md` という名前のフォルダ（開けないファイルの作り物）があります。
  直したり、消したりしないでください
- Windows と Mac の両方で、同じ `cases.json` を使います。パスの区切りは `/` で書いてありますが、Windows でもそのまま使えます

### テストだけでは足りないこと

テストの材料に合格しても、それだけで安全とは言えません。それぞれの `SPEC.md` の「作り方の手順」に、
**テストの材料では確認できない部分**（自己試験で確認すること・実際のファイルで確認すること）と、
**書いた本人以外の目に読ませること**が書いてあります。そこまで済んでから、使い始めてください。

とくに `pdf-encrypt` のケースは、保存したパスワードで開けること・空のパスワードでは開けないことまで確認しますが、
**毎回違うパスワードになること・権限のパスワードがどこにも保存されないことは、ケースでは確認できません。**
プログラムの自己試験（`--selftest`）と、社長が実際に PDF を開く確認（その `SPEC.md` の「作り方の手順」）で確認します。

## 仕様が新しくなったとき

`SPEC.md` の「仕様のバージョン」が、作ったプログラムの先頭に書いたバージョンより大きくなっていたら、
仕様が変わっています。新しい仕様を読み、プログラムを直して、新しい `cases.json` の全ケースに合格させてください。
